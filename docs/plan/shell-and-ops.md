## Latent bugs in the current setup (fix first)

1. **Dev and release builds share the owner's real database.** Both use identifier `dev.nash.kintsugi`. `pnpm tauri dev` run by an agent, or by the owner on a feature branch, applies unmerged migrations to the real `kintsugi.db`. After that, the main-branch build refuses to open it: sqlx's `ignore_missing` defaults to false, so `MigrateError::VersionMissing` follows. Fix: under `cfg!(debug_assertions)` use `kintsugi-dev.db`, and honour a `KINTSUGI_DB_PATH` override.
2. **A panic in a background task kills the release app silently.** The root `Cargo.toml` has `panic = "abort"`, so in release a panic in a spawned sync task aborts the whole process. In dev it only becomes a `JoinError`. Release also sets `windows_subsystem = "windows"`, so the `eprintln!` in `run()` goes nowhere. Recommendation: remove `panic = "abort"` (the cost is a little binary size) and install a panic hook that writes to the log.
3. **Two tests break with the first new migration.** `crates/core/tests/db.rs` asserts `applied_migrations == 1` in two tests. Assert against an exported `tracker_core::db::migration_count()` (`MIGRATOR.iter().count()`) instead.
4. **The frontend silently drops new error kinds.** `toApiError` in `src/lib/api.ts` hard-codes the kinds, so a kind added in Rust arrives as `"unknown"` with no failure anywhere.
5. **CI runs every PR twice.** `on: push` (all branches) plus `pull_request` runs both, and the concurrency groups differ (`refs/heads/x` vs `refs/pull/N/merge`), so they never cancel each other. Use `push: branches: [main]`. Also, `Swatinem/rust-cache` saves from every branch; add `save-if: ${{ github.ref == 'refs/heads/main' }}`.
6. **No CSP.** `"csp": null` in `tauri.conf.json` means none at all.
7. **PR order.** PR #2 contains PR #1's commit (same `vite.config.ts` and `decisions.md` hunk). Merge #1 first, then rebase #2.

## 1. Long-running work: sync as a background task

**Recommendation: events for status, plus a `sync_status` command for the initial state. No Channel, no polling.**

- A Channel is created by the frontend and passed into one `invoke` (`new Channel(); invoke('x', { onProgress })`), so it only works for syncs the frontend starts.
- The periodic sync is started by Rust with no frontend caller, and every mounted screen should see sync state. That is broadcast, which is what `Emitter::emit` is for.
- Progress is low-frequency (one message per page or judge), so events' throughput limits don't matter.
- Polling adds timers and test complexity for nothing.

**Permissions.** `core:default` is generated in `tauri-2.12.5/build.rs` as every core plugin's `:default`. `core:event:default` includes `allow-listen`, `allow-unlisten`, `allow-emit` and `allow-emit-to`, so `capabilities/default.json` needs no change.

**Design:**

- **Core (no Tauri):** `pub async fn sync(pool, client, cancel: &CancelToken, on_progress: impl FnMut(SyncProgress)) -> Result<SyncReport>`.
  - `CancelToken` wraps `tokio::sync::watch`. Core checks it between HTTP requests and before each per-page transaction, and its rate-limit sleeps use `tokio::select!` on it.
  - Cooperative cancel gives a clean "cancelled" result. `JoinHandle::abort` mid-transaction works (sqlx rolls back on drop) but reports nothing.
  - tokio is already in the tree; core needs it as a direct dependency with `sync` and `time` (one line in decisions.md).
- **Shell:** `SyncState(std::sync::Mutex<SyncSlot>)` holding `Option<RunningSync { id, cancel, started_at }>`, a `seq: u64` and the last status.
  - `try_start()` returns `Started(id)` or `AlreadyRunning(id)`. Never hold the lock across `.await`.
  - The spawned task clears the slot through a drop guard.
  - These are plain methods with unit tests and no Tauri runtime.
- **Commands:**
  - `start_sync` returns `{ runId, alreadyRunning }`. A collision is not an error, since the periodic and manual triggers can collide.
  - `cancel_sync`.
  - `sync_status` returns the snapshot.
- **Event:** `sync://status`, with payload `{ seq, state: "idle"|"running"|"finished"|"failed"|"cancelled", progress?, error?: ApiError }`.
  - The frontend subscribes first, then calls `sync_status`, and keeps whichever has the higher `seq`.
  - Failures reuse the `CommandError` shape.
- **Frontend:**
  - `api.ts` gets `onSyncStatus(handler): Promise<UnlistenFn>`.
  - Extend the ESLint `no-restricted-imports` rule to `@tauri-apps/api/event`.
  - In `useEffect`, clean up with `p.then(unlisten => unlisten())`, which survives the StrictMode double mount.
- **Periodic sync:** spawn a scheduler in `setup`. It waits about 60 s, then checks every 15 min. If the DB is Ready, auto-sync is on, and the last successful sync is older than the interval, it calls `try_start()`.
  - Interval and last-sync time live in the DB (schema planner's tables).
  - Failures update status only; no modal.

## 2. Managed state and the command pattern

Add `DbState::pool(&self) -> Result<&Pool, CommandError>` so each command opens with `let pool = db.pool()?;`. The `match` in `commands.rs` goes away.

**Arguments:**

- Closed sets (judge) are serde enums.
- User input (handles) arrives as `String` and is parsed by a core function returning `Error::Validation`. Tauri's own deserialise errors are plain strings and show up as `unknown`, which is fine for programmer errors.

**Kinds:** grow `ErrorKind` to `databaseUnavailable`, `database`, `validation`, `notFound`, `network`, `rateLimited`, `upstream` (judge returned an error or a payload we couldn't parse), `busy` (reserved for edits blocked by a running sync), `cancelled` and `internal`. Map `tracker_core::Error` with an exhaustive `match` and no wildcard, so every new core variant forces a mapping decision.

**TS types:**

- Now: hand-write them, with a drift guard on each side.
  - Rust: a unit test serialises every `ErrorKind` and asserts the exact string list (`serde_json` dev-dependency; it is already in the lockfile through tauri).
  - TS: `export const API_ERROR_KINDS = [...] as const`, with `toApiError` checking against it, and a test asserting the same list. Each test's comment names the other.
- Later: when the sync and review DTOs land (roughly 8 or more types), adopt **ts-rs as a dev-dependency only**. Use `#[cfg_attr(test, derive(TS))]`, export to `src/lib/generated/` during `cargo test`, and add a CI step `git diff --exit-code src/lib/generated`. It adds no runtime code, reads serde attributes, and generates types only, so the hand-written wrappers in `api.ts` stay.
- Not tauri-specta. Assumption: it is still a release candidate. It also wants to generate the command bindings, which conflicts with the `api.ts` rule.

## 3. Database operations

**sqlx 0.9 defaults** (from `options/mod.rs`):

- `foreign_keys = ON`
- `busy_timeout` 5 s
- `journal_mode` not set, so SQLite's DELETE mode
- `synchronous` not set, so FULL
- pool `max_connections` 10

**Set in `open()`:** `.journal_mode(Wal).synchronous(Normal)`, plus explicit `.foreign_keys(true).busy_timeout(5s)` so they are documented.

- WAL lets screens read while the sync writes.
- NORMAL is corruption-safe under WAL; at worst it loses the last transaction, which a re-sync recovers.

**Open sequence:**

1. If `_sqlx_migrations` holds a version unknown to the binary, return a new `Error::NewerDatabase { db, app }` before touching anything. The page then says "made by a newer Kintsugi".
2. If migrations are pending and the DB already has tables, run `VACUUM INTO ?` to `<dir>/backups/kintsugi-<ts>-pre-<version>.db`.
   - Get the timestamp from SQLite's `strftime`, so no chrono.
   - Keep the newest 5 backups.
   - `VACUUM INTO` gives a consistent copy under WAL; a raw file copy does not.
3. Run the migrator. Each migration runs in its own transaction; on failure, the backup is the way back.

**Export:** an `export_database` command does `VACUUM INTO` to `download_dir()/kintsugi-export-<ts>.db` and returns the path. This needs no dialog plugin.

- The .db file is the portable format (sqlite3, DB Browser). JSON export is deferred.
- Import (replace the DB and restart) is deferred. README documents a manual restore: quit, copy the backup over `kintsugi.db`, delete the `-wal` and `-shm` files.

**Tests:** these are file-based, in a unique temp dir per test: WAL is set, the newer-DB refusal, the backup is created only when migrations are pending, and retention.

## 4. Network policy

- HTTP lives in core: one shared `reqwest::Client` built in setup and held in state. It needs no Tauri capability, and CSP doesn't govern it.
- Client settings:
  - `connect_timeout` 10 s, total timeout 30 s, gzip.
  - User-Agent `kintsugi/<CARGO_PKG_VERSION>`, optionally with a repo URL (open question).
- Map errors to kinds: connect failures to `network`, HTTP 429 or the judge's "call limit" to `rateLimited`, schema or parse failures to `upstream`.
- Offline, the app keeps working from SQLite, and the scheduler just records the failure.
- **No test may touch the network.** Use recorded fixtures and a `base_url` parameter. Per-judge rate limits belong to the sync planner.
- **CSP:** set `csp` to `default-src 'self'; img-src 'self' data:; style-src 'self'; connect-src ipc: http://ipc.localhost`. This locks the webview out of fetching judges directly.
  - Set a separate `devCsp` (`tauri-utils` config: `csp` "is also injected on dev" unless `devCsp` is set) that adds `'unsafe-inline'` to `style-src` for Vite's injected `<style>` tags, and `ws://localhost:1420`/`1421` for HMR.
  - The design system's React `style={{…}}` props go through the CSSOM, so CSP doesn't block them.
  - Assumption: verify in `tauri dev` and in a release build on Windows.

## 5. Logging

Use `tauri-plugin-log` on the Rust side only: no JS package and no capability.

- Targets: `LogDir` (on Windows, under `%LOCALAPPDATA%\dev.nash.kintsugi\logs`) and `Stdout`.
- Level: Info (Debug in dev builds), with sqlx at Warn. sqlx logs through `tracing`, which forwards to `log`.
- Size cap of about 1 MB with a few rotated files.
- Register it first in the builder.
- Core uses the `log` facade (already in the tree). Never log response bodies.
- Add a `diagnostics` command and section with app version, DB path, schema version, log dir and last sync.
- Why not tracing plus an appender: that is more crates for the same result.

## 6. CI

- **Windows job: yes**, scoped to `pull_request` and `push` to main.
  - It catches MSVC linking, path and file-locking test bugs (the temp-dir DB test), and line-ending issues on the owner's platform.
  - Steps: toolchain, rust-cache, pnpm, `pnpm install`, `pnpm build`, `cargo clippy`, `cargo test`, `pnpm test`.
  - Skip fmt, lint and typecheck there; they don't depend on the platform.
  - Cost: Windows minutes are billed at 2× on private repos and free on public ones (open question).
- **Deferred, recorded in decisions.md:** `tauri build` and installers, signing, the updater. `bundle.targets: "all"` already gives the owner MSI and NSIS locally; unsigned builds trigger SmartScreen; the updater needs signing keys and hosting.

## 7. Dev experience: AGENTS.md and README additions

- **Background work:** a core function takes a `CancelToken` and a progress callback; the shell spawns it. Events are named `domain://name`, each has an `api.ts` wrapper, and the payload type sits next to it.
- **Error kinds:** adding one means editing the Rust enum, the TS list and both drift tests.
- **Network:** no test hits the network; HTTP lives only in core.
- **Database:** `tauri dev` uses `kintsugi-dev.db`. Never open the real database.
- **README:** logs, backups and export locations; the restore procedure; dev vs release DB.
- **Overnight checklist (`docs/agent-checklist.md`):**
  - One branch per task off a fresh `main`; rebase before the PR.
  - The done gate, pasted into the PR.
  - State what wasn't verified (GUI, Windows).
  - No edits to merged migrations; no new dependency without a decisions.md line.
  - Stop and ask on data-destroying migrations or loosened checks.
  - Leave stacked PRs clearly labelled.
